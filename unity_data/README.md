# Unity Data Export for 3D Printer Digital Twin

This directory contains Unity-ready CSV files for simulated sensor data playback in a 3D printer digital twin visualization.

---

## Files

| File | Description | Rows | Purpose |
|------|-------------|------|---------|
| `unity_sensor_playback.csv` | Window-level sensor data with health, anomaly, and maintenance | 885 | Display vibration, health, anomalies, and maintenance recommendations |
| `unity_electrical_playback.csv` | Electrical power measurements with printing stages | 10,861 | Display voltage, current, power, and printing stage |
| `unity_data_schema.json` | Complete schema documentation | - | Data types, units, field mappings, and limitations |
| `UNITY_INTEGRATION_GUIDE.md` | Unity 6.3 LTS integration guide | - | C# scripts, setup instructions, and troubleshooting |

## Source Data

### Primary Source Files

1. **Sensor Data**: `data/processed/sensor_data_with_health_anomaly.csv`
   - Generated by: `health_anomaly_pipeline.py`
   - Contains: Window-aggregated vibration features (Ax, Ay, Az), gyroscope data (Gx, Gy, Gz), health scores, anomaly detection results
   - Processing: Feature extraction, statistical baseline calculation, Isolation Forest anomaly detection, health indicator calculation

2. **Electrical Data**: `data/processed/electrical_context.csv`
   - Generated by: `electrical_analysis.py`
   - Contains: Voltage, current, active power, apparent power, power factor, printing stage labels
   - Processing: Power calculations from scope measurements

### Processing Pipeline

```
Original Dataset (SensorDataFile.csv, Gyroscope_SensorDataFile.csv, Scope runs)
    ↓
feature_extraction.py (window-level features)
    ↓
health_anomaly_pipeline.py (health scores, anomaly detection)
    ↓
sensor_data_with_health_anomaly.csv
    ↓
export_unity_data.py (this script)
    ↓
unity_sensor_playback.csv
```

```
Original Dataset (Scope CSV files)
    ↓
electrical_analysis.py (power calculations)
    ↓
electrical_context.csv
    ↓
export_unity_data.py (this script)
    ↓
unity_electrical_playback.csv
```

## Maintenance Recommendation Logic

The maintenance recommendations are added by `export_unity_data.py` using rule-based logic mirroring the backend:

```python
if condition_state == "NORMAL":
    recommendation = "NO_ACTION"
    priority = "LOW"
    message = "Machine operating normally. Continue regular monitoring."
elif condition_state == "WARNING":
    recommendation = "MONITOR"
    priority = "MEDIUM"
    message = "Machine health degraded. Increase monitoring frequency."
else:  # ABNORMAL
    recommendation = "INSPECT"
    priority = "HIGH"
    message = "Machine condition abnormal. Schedule inspection and maintenance."
```

This matches the logic in `backend/services/data_service.py`.

## Data Limitations

### Missing Fields

The following commonly expected sensor fields are **NOT AVAILABLE** in the original dataset:

- **Temperature**: Not present in the original sensor data
- **Humidity**: Not present in the original sensor data

These fields have been intentionally omitted rather than invented. If you need temperature or humidity readings in Unity, you would need to:
1. Collect new sensor data with temperature/humidity sensors
2. Update the processing pipeline to include these fields
3. Regenerate the Unity export files

### Temporal Misalignment

- **Sensor data**: Window-level aggregated features (885 windows over ~28 minutes)
- **Electrical data**: 250ms sample rate (10,861 samples over ~45 minutes)
- **Cannot be synchronized**: Different timestamps and resolutions
- **Recommendation**: Display as separate contexts in Unity UI

### Historical Data

- Timestamps reflect original recording time (2005-12-22 for sensor, 1970-01-01 for electrical)
- This is historical recording, not live ESP32 streaming
- Suitable for playback/simulation, not real-time monitoring

### Aggregated vs Raw Data

- Sensor data is window-aggregated features (mean, std, rms, etc.)
- Not raw time-series sensor readings
- Suitable for high-level status display, not detailed waveform visualization

## Health Score Calculation

Health scores are calculated in `health_anomaly_pipeline.py`:

```python
# Health indicator based on deviation from normal baseline
deviation = abs(value - baseline_mean) / baseline_std
health_contribution = max(0, 1 - deviation / 3.0)
health_score = mean(health_contributions) * 100  # Convert to percentage
```

**Condition states:**
- NORMAL: health_score >= 80%
- WARNING: 50% <= health_score < 80%
- ABNORMAL: health_score < 50%

---

## Anomaly Detection

Two methods are used:

1. **Statistical Threshold**
   - Z-score based: deviation > 3 standard deviations from mean
   - Field: `statistical_is_anomaly`

2. **Isolation Forest**
   - Unsupervised ML with 5% contamination
   - Field: `isolation_forest_is_anomaly`
   - Unity uses this method for `anomaly_detected` field

## Regenerating the Export

To regenerate the Unity CSV files from processed data:

```bash
# From project root
python export_unity_data.py
```

This will:
1. Load `data/processed/sensor_data_with_health_anomaly.csv`
2. Load `data/processed/electrical_context.csv`
3. Add maintenance recommendations
4. Export `unity_data/unity_sensor_playback.csv`
5. Export `unity_data/unity_electrical_playback.csv`
6. Generate `unity_data/unity_data_schema.json`
7. Validate outputs and report statistics

**Requirements:**
- Python 3.7+
- pandas, numpy
- No live ESP32 connection required
- No backend/FastAPI required
